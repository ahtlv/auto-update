# Скилл `auto-update` — дизайн

**Дата:** 2026-06-18
**Статус:** утверждён (brainstorming), v3 — реестр в блочном формате (после ресёрча)
**Автор:** Анатоль + Claude

## Проблема

Окружение для вайбкодинга разрослось: плагины Claude Code, MCP-серверы,
git-репозитории со скиллами и submodules, локальные тулзы. Обновления выходят
часто (например, Superpowers от obra), но узнать «что устарело и что именно
изменилось» можно только обходя каждый компонент вручную. Ручной обход
ненадёжен — легко забыть компонент или снести не то (реальный случай:
при ручной чистке дубля Superpowers была удалена свежая версия вместо старой).

Нужна одна точка входа: «запусти автоапдейтер» → получить отчёт, что вышло
нового по всему хозяйству, и выборочно обновить.

Дополнительно: автоапдейтер должен быть **распространяемым продуктом** —
Анатоль ведёт курс по Claude Code, студенты должны устанавливать его себе и
периодически проверять своё окружение. Значит, движок нельзя завязывать на
личные компоненты Анатоля.

## Цели

- Единый скилл, проверяющий **все** классы компонентов окружения.
- **Read-only по умолчанию:** сначала отчёт, апдейт — только по явному выбору.
- Отчёт показывает версию X→Y, краткое «что изменилось» и флаг возможных
  breaking changes.
- Реестр компонентов **самоподдерживается**: новые компоненты подхватываются
  (через discovery при запуске и через правило дописывания при установке).
- **Универсальность:** движок не содержит ничьих личных компонентов и работает
  у любого пользователя «из коробки».
- **Дистрибуция:** публичный репозиторий + `install.sh`; студент ставит за одну
  команду, обновляет через `git pull`.
- **Версионность и self-update:** semver, CHANGELOG, теги; автоапдейтер умеет
  обновлять сам себя.

## Не-цели (YAGNI)

- Не автоматический фон/cron (запуск только вручную; cron — возможное будущее).
- Не откат версий (rollback) — вне объёма первой версии.
- Не управление версиями самих проектов (atelier, claudekurs и т.п.) — только
  инструментальное окружение.
- Не глубокий risk-анализ release notes — глубина «средняя».
- Не оформление в виде Claude-plugin/marketplace в первой версии (выбран путь
  «репо + симлинк»); миграция в полноценный плагин — возможное будущее.

## Архитектура: два слоя

Ключевое для распространяемости — **разделить движок и данные пользователя**,
чтобы обновление движка никогда не затирало персональный реестр.

### Слой 1 — Движок (репозиторий, шарится)

Публичный репо `ahtlv/auto-update`, клонируется в `~/Work/auto-update`.

```
~/Work/auto-update/
├── SKILL.md              # инструкция Claude: оркестрация 5 фаз
├── check.sh              # детерминированный чекер версий → машинный вывод
├── registry.example.conf # ШАБЛОН реестра: закомментированные образцы всех типов
├── install.sh            # bootstrap: симлинк + создание персонального реестра
├── VERSION               # текущая версия (semver)
├── CHANGELOG.md          # история версий движка
└── README.md             # установка и использование (для студентов)
```

Версионируется, обновляется через `git pull`. Не содержит ничьих личных данных.

### Слой 2 — Персональный реестр (у каждого свой, НЕ в репо)

```
~/.claude/auto-update/
└── registry.conf         # личный список компонентов пользователя
```

Создаётся при установке, наполняется фазой DISCOVER, **никогда не затирается**
обновлением движка. Per-machine: на каждой машине свой реестр со своими
компонентами (это снимает необходимость в `hosts:` в общем случае).

### Симлинк

`install.sh` создаёт `~/.claude/skills/auto-update -> ~/Work/auto-update`, чтобы
Claude Code увидел скилл. (Для Анатоля, у кого `~/.claude/skills` = репо
claude-config, симлинк добавляется в `.git/info/exclude`, чтобы не коммитить
чужую папку в личный конфиг.)

### Подход «гибрид» (без изменений)

- `check.sh` — детерминированно сравнивает локальную и удалённую версию каждого
  компонента из реестра. Read-only. Машинный вывод. Может запускаться автономно.
- `SKILL.md` (Claude) — оркеструет 5 фаз: чекер, discovery, ресёрч changelog,
  отчёт, диалог выбора, апдейты, дописывание реестра.

## install.sh

Идемпотентный bootstrap (можно запускать повторно безопасно):

1. Определить путь репо (директория самого `install.sh`).
2. Создать симлинк `~/.claude/skills/auto-update` → путь репо (если ещё нет).
3. Создать каталог `~/.claude/auto-update/` (если нет).
4. Если `~/.claude/auto-update/registry.conf` **не существует** — создать из
   `registry.example.conf` (или пустой каркас). Существующий не трогать.
5. Дописать в персональный реестр запись о самом `auto-update` (тип `git-repo`,
   `path` = путь репо) — для self-update.
6. Подсказать: перезапустить сессию Claude и сказать «запусти автоапдейтер».

## Поток работы — 5 фаз

1. **CHECK** — запустить `check.sh`. По каждому компоненту из реестра сравнить
   локальную и удалённую версию средствами под тип. Ничего не изменяет.
2. **DISCOVER** — просканировать систему на компоненты вне реестра (плагины,
   git-репо в `~/Work`, MCP-серверы из конфигурации). Найденное предъявить:
   «добавить в реестр?» → дописать в `registry.conf`. **При пустом реестре
   (первый запуск у нового пользователя) эта фаза = онбординг.**
3. **RESEARCH** (по устаревшим, глубина «средняя») — краткое «что изменилось»
   (`git log` / CHANGELOG / release notes) + флаг ⚠️ при признаках breaking
   changes (мажорный bump; breaking/removed/migration в заметках).
4. **REPORT** — таблица-отчёт (формат ниже). Актуальное — свёрнуто. Запросить
   выбор: всё / номера / только без ⚠️ / ничего.
5. **APPLY** — апдейт-команды под тип **только для выбранного**; для `git-repo`
   с `post_update` — пост-хук. Итог: что обновлено, пропущено, что требует
   рестарта сессии Claude.

## Формат отчёта (фаза REPORT)

Актуальное — свёрнуто, чтобы взгляд цеплялся за устаревшее. ⚠️ = подозрение на
breaking changes. Нумерация — для выбора в диалоге.

```
🔄 Авто-апдейт окружения

ПЛАГИНЫ
  1. superpowers        6.0.2 → 6.1.0    ✦ новый skill foo, фикс бара
МCP-СЕРВЕРЫ
  2. telegram-mcp       3 коммита позади ✦ фикс auth-timeout
     cve-mcp-server     актуально ✓
РЕПО/СКИЛЛЫ
     claude-config      актуально ✓
  3. cybersec-skills    +12 скиллов      ⚠️ изменилась структура индекса
ТУЛЗЫ
  4. yt-dlp             2025.06.01 → 2025.06.15
     ffmpeg             актуально ✓

🆕 ВНЕ РЕЕСТРА: ~/Work/some-new-mcp (git-repo) — добавить?

Что обновляем? [всё / номера через запятую / только без ⚠️ / ничего]
```

## Схема `registry.conf`

`type` задаёт дефолтные команды check/update; в записи указывается только то,
что отличает компонент. Нестандартное — через `type: custom` с явными командами.

Блочный формат: один компонент = блок строк `key=value`, блоки разделяются
пустой строкой, `#` — комментарий, ключ от значения отделяет ПЕРВЫЙ `=`.
Парсится ~10 строками BSD awk, без зависимостей; фаза DISCOVER дописывает
новый блок простым `>>`.

```text
name=superpowers
type=claude-plugin
marketplace=claude-plugins-official

name=telegram-mcp
type=git-repo
path=~/Work/telegram-mcp
post_update=uv sync

name=cybersec-skills
type=git-submodule
parent=~/Work/myOS
path=.claude/skills/cybersec-skills

name=mlx_whisper
type=pip-venv
venv=~/.venv

name=ffmpeg
type=brew

# custom с optional latest: agent-browser сравнивает installed↔npm
name=agent-browser
type=custom
check=AB=$(ls ~/.nvm/versions/node/*/bin/agent-browser | tail -1); "$AB" --version | awk '{print $NF}'
latest=command npm view agent-browser version
update=command npm install -g agent-browser@latest

# claude-cli: latest не определить read-only → INFO, update применяет
name=claude-cli
type=custom
check=claude --version | awk '{print $1}'
update=claude update

# self-update, дописывается install.sh
name=auto-update
type=git-repo
path=~/Work/auto-update
```

### Типы компонентов и их дефолтные команды

| type | check | update | примечание |
|------|-------|--------|------------|
| `claude-plugin` | `claude plugin list` vs маркетплейс | `claude plugin marketplace update --all` → `claude plugin update <name>@<marketplace>` | сначала обновить маркетплейс |
| `git-repo` | `git fetch` + `rev-list --count HEAD..@{u}` | `git pull` + `post_update` | пост-хук опционален |
| `git-submodule` | fetch + сравнение с remote-веткой | `git -C <parent> submodule update --remote <path>` | |
| `brew` | `brew outdated <name>` | `brew upgrade <name>` | |
| `pip-venv` | `<venv>/bin/pip list --outdated` | `<venv>/bin/pip install -U <name>` | |
| `custom` | поле `check` (+`latest` опц.) | поле `update` | для нестандартных тулз |

**Поля записи:** `name` (обязательно), `type` (обязательно), `path`/`parent`/
`venv`/`marketplace` (по типу), `post_update` (опц.), `check`/`latest`/`update`
(для `custom`; если `latest` задан — сравнивается с `check`, иначе статус INFO),
`hosts` (опц. — парсится, но в v0.1.0 не используется: реестр per-machine).
Значения берутся ВЕРБАТИМ (триммится только ключ) — в них можно свободно
использовать `=`, пробелы, кавычки, `&&`, `|`.

### registry.example.conf

Шаблон в репо: закомментированные образцы **каждого** типа с пояснениями, чтобы
пользователь видел синтаксис. Реальные компоненты не перечисляет — их добавляет
DISCOVER при первом запуске.

## Версионность и self-update

- `VERSION` (semver) + git-теги `vX.Y.Z` + `CHANGELOG.md` в репо движка.
- Автоапдейтер регистрирует **сам себя** в персональном реестре как `git-repo`
  (запись добавляет `install.sh`). При апдейте этой записи — `git pull` репо
  движка; после — подсказка перезапустить сессию Claude.
- Так обновление движка идёт через тот же механизм, что и всё остальное.

## Универсальность (требования к движку)

- `check.sh` и `SKILL.md` **не хардкодят** пути и компоненты конкретного
  пользователя — всё берётся из `~/.claude/auto-update/registry.conf`.
- `~` в путях реестра раскрывается в домашний каталог текущего пользователя.
- Отсутствующие на машине компоненты **молча пропускаются** (graceful skip), не
  роняя прогон.
- Зависимости движка минимальны: bash + git + то, что чекаемые тулзы и так
  требуют. Парсер `registry.conf` не должен требовать установки `yq` (см.
  открытые вопросы).

## Дистрибуция (для студентов)

- Публичный репо `ahtlv/auto-update`.
- Установка: `git clone https://github.com/ahtlv/auto-update ~/Work/auto-update`
  → `cd ~/Work/auto-update && ./install.sh`.
- Обновление: автоматически через сам автоапдейтер (self-update) или вручную
  `git pull`.
- `README.md` — кратко: что это, установка, как запускать, как добавить
  компонент вручную, как обновлять.

## Самопополнение реестра

1. **DISCOVER при запуске** (фаза 2) — ловит появившееся в системе.
2. **Правило при установке** — добавить в `claude-config/rules/` правило: когда
   Claude в любой сессии ставит новый MCP / плагин / клонирует репо со скиллами —
   сразу дописать запись в персональный `registry.conf`. (Это правило — личное
   для Анатоля, в дистрибутив движка не входит.)

## Решённые вопросы (ресёрч 2026-06-18, проверено на машине)

- **Парсинг реестра без `yq`:** `yq` не установлен → отказ от YAML в пользу
  блочного `key=value` формата + awk-парсер (10 строк, протестирован). См. план,
  Задача 2.
- **Формат вывода `check.sh`:** TSV `status⇥name⇥type⇥installed⇥latest⇥detail`
  (Claude читает легко; append-friendly).
- **Сравнение версии плагина:** `claude plugin list --available` НЕ годится
  (прячет уже установленный плагин). Метод — jq-сравнение `installed_plugins.json`
  vs `marketplace.json`, ветвление version-pin / git-sha-pin. Офиц. маркетплейс
  отдаётся через GCS (нет `.git`), сторонние — git-клоны. См. план, Задача 6.
- **Рестарт сессии Claude:** требуется для плагинов/скиллов — фиксируется в отчёте
  фазы APPLY.
- **`install.sh` и симлинк:** `~/.claude/skills` САМ симлинк в `claude-config/skills`
  → наивный `ln -s` попал бы в git-репо. Решение: ветвление + `.git/info/exclude`
  (idempotent). См. план, Задача 12.
- **Прочие находки:** `npm`→алиас `pnpm` (использовать `command npm`);
  `agent-browser` под nvm-путём (глоб, не хардкод версии node); `brew outdated`
  с `HOMEBREW_NO_AUTO_UPDATE=1`; у `claude` нет read-only проверки апдейта.

## Критерии готовности

- `git clone` + `./install.sh` у **чистого** пользователя ставит скилл, создаёт
  пустой персональный реестр и регистрирует self-update.
- Первый запуск у нового пользователя через DISCOVER предлагает внести
  найденные компоненты — реестр наполняется без ручной правки.
- CHECK корректно определяет устаревшие компоненты всех типов.
- REPORT читается с одного взгляда: устаревшее видно, актуальное свёрнуто,
  breaking помечено ⚠️.
- APPLY обновляет только выбранное и выполняет пост-хуки.
- `git pull` движка **не затирает** персональный реестр.
- На машине без части компонентов прогон не падает (graceful skip).
- Движок не содержит личных компонентов/путей (проверяется ревью репо).
